### Database constraints needing deliberate treatment

- The lifecycle migration's `applications_state_check` permits only the five existing states. `applications_one_active_configuration` covers those same five states for institution/module/manifest. Adding final states without deciding D9 would implicitly change repeat-application behavior.
- [Coherence migration](../database/migrations/2026_10_19_400002_enforce_phase_3d_state_coherence.php)::enforce_application_transition permits only the existing transitions; immutable application bindings remain fixed; state changes require lock_version +1. Current submission must belong to the case, current working revision must be its open revision. Submitted/under_screening/resubmitted require current submission and no working revision; correction_requested requires both.
- Working revision consumption is one-way and binds the exact immutable submission. Consumed draft answer/evidence guards and append-only triggers protect submissions/answers/requirements/evidence membership/history/screening/correction records. Keep all protections.
- [Binding migration](../database/migrations/2026_10_19_400001_harden_phase_3d_application_guards.php) validates exact application/working revision/draft/manifest/question/requirement/evidence and correction targets. Do not rewrite snapshots, move routing, or loosen these guards for a decision/document.
- Existing tracking labels, queue filters and consumers understand current states; review all state-dependent reads when extending them. Do not alter existing screening/correction edges or assume catalogue region changes reroute submitted cases.

## 3. Proposed decision operation and persistence

**PROPOSED — REQUIRES OSDS CONFIRMATION; technical design subject to implementation review:**

1. Accept case public ID, expected current submission ID/public UUID and application lock version, outcome, approved reason/attestation fields and a request key. Ignore caller actor, region, institution and attribution fields.
2. Own one PostgreSQL transaction, one attempt. Lock exact case and narrowly relevant actor/authority/prerequisite records using reviewed existing ordering; reload state and authorize after waits. Reuse existing scope semantics without assuming a mounted User/assignment remains fresh. Document required lock order and test competing authority changes.
3. Bind decision to current immutable submission; compare expected version/revision. Reject stale/foreign-revision/opposite competing actions without partial writes. Candidate one final decision per application is subject to D6; enforce through database constraints as well as service checks.
4. Persist append-only decision ID/UUID, case/submission, outcome, actor/time, approved validation evidence and applicant summary/internal reason separation; update state/version and append history. Add only approved new explicit audit semantics, tentatively `application.demo_approved` / `application.demo_rejected`; names/metadata remain proposals. Include IDs, sequence and correlation, not raw evidence URLs or sensitive answers.
5. Commit decision/history/state/audit together. Audit failure before or after actual audit insertion must roll back the operation. Preserve existing submission/screening/correction writers; no Core observer registration or duplicate manual audit is assumed.
6. Candidate request-key uniqueness returns the existing same operation only **after current authorization**; different conflicting request fails safely. This is proposed new decision idempotency, not a claim about every existing workflow. Never execute a new decision automatically after uncertainty.

A future forward migration must narrowly extend the state check and latest transition/coherence function for the approved two edges, preserve identity/version guards, define final-state submission/no-working-revision coherence, and resolve active-case uniqueness explicitly under D9. Add decision/document structures only after approval; do not edit historical migrations or existing records. Migration/rollback safety and constraints require review before execution.

All contents of this section are **PROPOSED — REQUIRES OSDS CONFIRMATION (D7–D10)**, including audience, retention and event names. One approved versioned outcome-summary template; approval/rejection variants only if confirmed. PDF is a candidate format, not an imposed legal document requirement.

| Element | Proposed minimum |
| --- | --- |
| Template identity | Immutable version ID, module, document kind, outcome applicability, owner approval reference/time, content hash and allowed merge-field schema. Store approved wording, not arbitrary uploaded executable template code. |
| Visible required fields | Repeated **DRAFT / DEMONSTRATION ONLY** marking; confirmed module/title; internal demonstration case reference clearly not an official number; organization name from submitted snapshot; submission sequence/date; demonstration outcome/date and approved applicant-facing summary; template version and generation timestamp. No signature image, official serial, legal validity or assertion of issuance. |
| Provenance | Document ID/UUID → decision ID → exact ApplicationSubmission ID/UUID/sequence and its hashes; template version/hash, renderer version, input snapshot/hash, output checksum, generator/time and correlation. Do not merge changing live applicant/catalogue values over the submitted snapshot. |
| Data minimization | Whitelist merge fields; exclude evidence locators, credentials, sensitive answers and internal notes. Supervisor approves any additional personal fields. Watermark must be embedded in downloaded bytes, not only viewer chrome. |
| Access | Private artifact retrieval through current authorized case/document action. Check applicant/staff audience at request time; no public URL or unscoped direct file access. Preserve evidence/answer-specific permissions independently. |
| Audit | Proposed explicit draft-generation success event with document/decision/submission/template identifiers and actor, committed with artifact metadata. Download/view audit requirement is a separate supervisor decision, not an invented existing mandatory event. |
| Retention/regeneration | Owner-approved retention. Candidate one artifact per decision/template/input/renderer version; identical authorized requests return that artifact. New template/render version produces a separately linked artifact rather than overwriting history; confirm policy before implementing. |

**Recovery design proposal:** decision commits independently of rendering so renderer failure cannot falsely undo or repeat a committed decision. Generate from the immutable approved input; finalize ready metadata + generation audit in one operation transaction. File/object storage is not part of PostgreSQL rollback: keep staged bytes private and unadvertised until successful finalization, handle failed finalization as unavailable, and define controlled staging cleanup before implementation. Do not promise a cross-storage transaction or expose a file when the mandatory generation audit failed.

Rendering failure leaves decision/history intact and no falsely ready document. Show fixed redacted guidance/support reference, retain the page and permit an explicit authorized generation attempt. On lost decision/generation responses, inspect saved case/document state in another authorized view; do not automatically replay a consequential operation. A ready artifact can be retrieved only after fresh access checks. These are proposed contracts to test, not current capabilities.
