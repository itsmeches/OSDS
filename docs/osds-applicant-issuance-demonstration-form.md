# Applicant issuance demonstration form

**21 October 2026. Implemented under the user's confirmed demonstration-only scope.** Authorized applicants may answer a published form without an application-eligibility or issuance claim. No application approval, case/revision linkage, legal issuance, official number, signature or email delivery is implemented. Batch G remains CONDITIONAL CLOSE pending separate sign-offs.

## Use in the existing system

**Local login correction:** the original ApplicantAuthController rejected both login GET and POST when ApplicantSandboxGuard excluded `osds_dev`, so the resources were unreachable from applicant login despite their separate access policy. Login now permits the existing nonproduction resource surface, checks active identity and `applicant.portal.access`, and redirects resource-only local sessions to the issuance demonstration form. The full application sandbox still requires its original allowed database and synthetic identity; start/home/application/evidence guards are unchanged. Resource-only navigation hides those unavailable workflow links. No account, permission or database setting is modified by this correction. The live local login URL returned HTTP 200 with the resource-specific heading after the change.

Login-correction verification: the expanded applicant/issuance/document/download matrix executed **79 tests / 1,094 assertions: 77 passed, two new local-login fixture failures**. Switching the fixture environment to local enabled normal CSRF enforcement; the new test posts had omitted tokens. Adding valid session/request tokens, without changing runtime CSRF middleware, produced **2 tests / 20 assertions passed** (2,928 ms) for those local login cases: valid login and resource redirect, preserved application-route denial, missing permission/inactive account rejection and production 404. The 77 passing cases include the existing synthetic-only sandbox login tests. This is a reconciled combined attempt plus targeted rerun, not a new all-green 79-test or full-suite run. Touched PHP Pint passed. No credentials/accounts, database configuration, migrations or default-database records changed during the login fix.

1. **OSDS → Demonstration documents → Applicant issuance form settings.** Edit title, instructions and labels. Add/remove up to 12 short-text, long-text or date questions and choose whether answers are required.
2. Configure demonstration offices/directors in the existing regional-office directory. Check **Available to authorized applicants** and **Save applicant form**. Uncheck and save to withdraw it.
3. **Applicant → Demonstration issuance form** (`/applicant/issuance-demo`). Enter fictional details, select COR/ACSA and office, answer the configured questions, confirm demonstration use, then **Preview printable draft (new tab)**.
4. The rendered document uses the answers and the selected office's server-resolved director/designation. Print / Save as PDF in the browser. Additional answers print in a clearly marked demonstration appendix.

OSDS can change content without a release. Core merge fields keep their identities/types/required validation: certificate type, organization, address, demonstration date and office. Labels are editable, while arbitrary HTML, executable templates, client-supplied directors, legal validity and official numbers are not configurable through this form. Additional questions do not change legal certificate wording or replace merge fields. Existing questionnaire authoring/publication and application forms remain unchanged; this is a bounded editor for the independent demonstration-output form, not another application workflow.

## Access, versioning and persistence

- Management reuses existing `platform.admin.access` plus `forms.downloads.manage`; no role-name authority or new permission grant. Publication locks/reloads actor and relevant permission memberships, serializes the low-volume form-definition table, rechecks fresh authority and expected revision, and appends the definition plus `demonstration_issuance.form_published` audit in one transaction/one attempt. Earlier definitions have database append-only protection. Failed audit insertion rolls back publication.
- Applicants require fresh active identity and `applicant.portal.access`, in local/testing/sandbox only. This is a new independent nonofficial preview, including local `osds_dev`; existing ApplicantSandboxGuard and all submission/evidence/eligibility/representation policies are unchanged. No eligibility, regional jurisdiction or case access is inferred by choosing an office. CHEDRO without applicant permission cannot answer; applicants cannot edit definitions. Production is denied.
- Definitions and directory revisions are posted explicitly. Changed/withdrawn definitions, stale directories and unavailable offices reject preview; a refreshed form is required. Forged director/designation and unknown extra answers are excluded from the rendered result. Output is escaped and uses immutable template **demo-v3**, with form/directory revision identifiers and embedded **DRAFT / DEMONSTRATION ONLY** markings. Earlier demo-v1/v2 layouts remain preserved.
- Applicant answers and output bytes are **not durably saved as submissions/documents**. A preview is read-only and has no generation event or consequential retry. Form inputs remain in the original tab; framework validation may temporarily flash old input/errors in the session. Session/network loss does not promise durable recovery. Responses are private/no-store; no entered values are placed in query strings. Published labels and sample contents are not approved OSDS policy merely because a manager saved them.
- A downloaded/printed preview retains its rendered values after configuration changes, but no server-side case-linked document archive is claimed. Saved draft answers, immutable submitted issuance responses, ownership-bound historical retrieval and decision-linked generation remain future separately authorized work. Neither rendering nor ticking the demonstration box proves applicant eligibility.
