## ZIP import addition — 21 October 2026

OSDS can now open **Downloadable forms → Import forms from a ZIP**, choose the supplied archive, enter a version label and select **Import and publish forms**. Each PDF/DOCX/XLSX becomes a separate new catalogue entry with its filename as title and General / both modules applicability. This does not replace existing entries or infer authoritative module applicability. Individual replacement remains available for later changes. CHEDRO and applicants cannot import.

The archive is limited to 10 MB, 20 forms, 10 MB per form and 50 MB total expanded bytes. Unsafe paths, duplicate basenames, encrypted entries, unsupported files and nested archives are rejected. Existing per-file Office/PDF validation applies; this is not malware scanning. All catalogue rows, versions and existing per-file publication audits share one outer single-attempt transaction. A later validation/audit failure rolls back earlier entries and removes staged private bytes; temporary extraction files are removed. Process-crash orphan limitations remain as documented below.

New actual-page import coverage uses the preserved original five-file ZIP. Final focused PostgreSQL result: **20 tests / 172 assertions passed** (11,821 ms), including later-file validation rollback, audit insertion followed by failure on the second file, private-byte cleanup, path traversal rejection and CHEDRO denial. An initial test-harness run had two errors (Livewire fake-upload construction and a temporary PDF object lifetime); both were corrected. The intermediate 18 / 161 run passed before the additional fault/authority tests. Touched PHP Pint and tracked diff whitespace checks passed, with existing CRLF advisories. No new full-suite, browser, accessibility or build pass is claimed for this addition.

The original archive has **not been automatically imported into the existing application database**. Use the OSDS interface to publish it under the signed-in manager's identity. Repeated explicit imports create separate entries; inspect the catalogue after uncertainty before repeating. No migration, permission change, default-database mutation, automatic replay, deployment or phase progression was performed for this addition.

## Behavior and operation boundary

The later [UI/UX refinement](osds-downloadable-forms-ui-refinement.md) aligns this catalogue with existing questionnaire/portal cards, a collapsible editor, concise actions and secondary history. It changes presentation only; current permissions and version/download/audit behavior remain unchanged. Its new scoped browser/accessibility evidence is recorded separately.

- Staff panel: **Downloadable forms**, `/admin/downloadable-forms`. Active staff-panel admission plus `forms.downloads.view` or `forms.downloads.manage` permits viewing/current downloads. OSDS receives management; CHEDRO receives view only. Upload/replacement/withdrawal still require management authority on the server, not just hidden buttons. No role name alone bypasses checks.
- Applicant portal: **Downloadable forms**, `/applicant/forms`. Active applicants with `applicant.portal.access` can browse/download currently available blank forms but cannot manage them. Other accounts/guests cannot retrieve files. This local blank-form catalogue is separate from the guarded synthetic application workflow; existing workflow guards are unchanged.
- Managers enter title, optional instructions, module applicability (existing module or general/both), version label and PDF/DOCX/XLSX file, up to 10 MB. Replacement creates a new numbered version and republishes a withdrawn form. Withdrawal hides it; no historical version bytes are deleted. Managers can inspect version labels, filenames and checksums. Catalogue pages are paginated, ten entries per page.
- Files use generated private storage paths, sanitized download filenames and SHA-256 checksums. Office package structure/content type is checked, macro-enabled content rejected and archive entry/expanded-size limits applied. PDF MIME/header checks apply. This is not antivirus scanning or a guarantee all embedded document content is harmless. Only approved blank forms belong here.
- Downloads bind both form UUID and the current version. An old URL returns 404 after replacement/withdrawal rather than silently downloading different bytes. Responses use attachment disposition, private/no-store cache controls and nosniff. No historical-version download endpoint or public storage link is added. A previously downloaded local copy cannot be recalled.

`DownloadableFormService` owns the single-attempt operation transaction, locks/reloads actor and relevant permission memberships, rechecks current authority and locks the form before replacement/withdrawal. Expected current-version checks reject stale updates. Existing AuditRecorder writes one explicit `downloadable_form.published`, `.replaced` or `.withdrawn` event in that transaction. No Core observer is added and no unrelated audit contract changes.

Private file storage is not part of the PostgreSQL transaction. A unique upload is staged before the operation; only its uncommitted bytes are removed on caught failure. Prior versions remain intact. A process crash can leave a private unreferenced file; no automatic broad deletion job is introduced. Retention/controlled orphan cleanup remains a separately reviewed operational concern. A request already authorized/in progress can finish while another request withdraws the form; subsequent requests deny it. No universal race/idempotency claim.

## Deployment boundary and manual review

Initial verification used only `osds_test` and `osds_ui_browser_test`. The subsequent user-authorized integration applied only the targeted schema addition and additive OSDS permission to existing local `osds_dev`, as recorded above. No reset/reseed or full AuthorizationSeeder ran. Do not run the complete AuthorizationSeeder against manually customized permissions casually: it synchronizes role bundles. No production activation is included.

Manual review: sign in as an authorized manager, upload an approved blank form, inspect current download, replace it, verify new label/bytes and prior history, withdraw it and verify applicant access disappears. Confirm audience and module descriptions with OSDS. Keyboard/touch, native zoom, screen-reader notices and document print/layout acceptance are not certified by automated checks.

The dynamic principle applies to changeable catalogue content: staff can update files/title/instructions/applicability/version labels without a release. Security limits, permission policy and unrelated business workflows are intentionally not converted into arbitrary editable rules. Other submodules remain separate authorized slices. No commit, push, deployment, official issuance, Batch H or Phase 4.
